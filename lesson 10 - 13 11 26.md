#### Negation numbers and size limits (over flow)

#### Part 1: The bulbs run out

An 8-bulb holds 0 to 255. What happens if you add 1 to 255? there is no 9th bulb to hold the extra 1.

Think of the odometer in a car, which you already know. 

**Imagine** an odometer with only 5 wheels, showing 99999. Drive one more kilometer and it shows 00000. The wheels roll over and the extra “1” falls off the front.

Binary does exactly this:

```bash
  11111111   (255)
+        1
= 100000000  (needs 9 bulbs)
```

only 8 bulbs exist, so the leftmost 1 falls off, and the byte shows 00000000 = 0. 

So in an 8-bit counter, 255 + 1 = 0. This is called **overflow**, or wraparound.

The limit depends on the number of bulbs: <u>**n bulbs hold 0 to 2ⁿ − 1.**</u>

| Bulbs | Biggest number |
| --- | --- |
| 8 | 255 |
| 16 | 65,535 |
| 32 | 4,294,967,295 |

#### Part 2: How do we write negative numbers?

We have no “minus sign” bulb. So computers use a clever trick, again based on the odometer.

Start at 00000000 (zero) and go backwards by one click. The wheels roll the other way, so you get 11111111. We decide that this pattern means - 1. Go back one more: 11111110 means -2, and so on. This is called two’s complement.

The leftmost bulb now acts like a sign flag:

- 0 means zero or positive
- 1 means negative

Half the patterns are used for negatives, so an 8-bit signed number holds -128 to +127.

| Pattern | Read as unsigned | Read as signed |
| --- | --- | --- |
| 00000000 | 0 | 0 |
| 00000001 | 1 | 1 |
| 01111111 | 127 | 127 |
| 10000000 | 128 | −128 |
| 10000001 | 129 | −127 |
| 11111110 | 254 | −2 |
| 11111111 | 255 | −1 |

Look closely: the same bulbs can mean two different numbers. 11111111 is 255 or -1, depending on how the program was told to read it. The bulbs don’t know. The program decides.

**How to find a negative pattern (the flip trick)**

To write -5 in 8 bits:

1. **Write** 5: 00000101
2. **Flip every bit (0 ↔ 1):** 11111010
3. **Add 1:** 11111011

So -5 = 11111011. Check with a shortcut: as an unsigned number, 11111011 = 251, and 256 - 5 = 251

#### Part 3: Why this matters for security

Now see what happens at the top of the signed range:

```bash
  01111111   (+127)
+        1
= 10000000   (−128)
```

A big positive number just turned into big negative number. this is the **signed overflow**.

Real programs get hurt by this. A program might check “*Is the size of this data small enough?*” If the size wraps around into small or negative number, the check passes by mistake. Then the program copies far more data than it has space for. Many serious security bugs began exactly like this. it’s called an **integer overflow**, and it’s common cause of dangerous holes, so security engineers look for it on purpose.

Famous real-life examples:

→ In 2014, the YouTube view counter for the song “Gangnam Style” passed 2,147,483,647, the biggest value a signed 32-bit number can hold, and YouTube had to upgrade its counter. 

→ In 2015, aviation regulators warned that a Boeing 787 had a counter that could overflow after 248 days of continuous power. These show that even big, careful systems must think about the size limit.
